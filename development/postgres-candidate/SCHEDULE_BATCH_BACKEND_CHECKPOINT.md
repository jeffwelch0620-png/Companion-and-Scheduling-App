## Contract and authority

- Authenticated POST `/api/operations/<store>/batch-review` accepts `{weekStart,drafts}` for 1–100 unique drafts. Each row is `{id,revision,input:{personId,position,startLocal,endLocal,startOccurrence?,endOccurrence?}}`. Local fields have no offset and are resolved by the server in the configured store timezone; choices are `earlier`, `later` or blank. The parser normalizes IDs, ordering and local seconds/fractions. Unknown fields, duplicate IDs, overflow and invalid dates fail the whole envelope. No staffing rows, department/station edits, cancellation or publish flag are accepted.
- Review returns every row with authoritative before/after UTC and local times, retained station metadata, ready/rejected status, safe issues and counts. Unavailable or unauthorized sources expose only selected ID/revision and an unavailable issue. Names are not snapshotted here; future forms resolve current authorized employee labels through roster/shared employee reads.
- `shift.save-batch` adds a `reviewToken`, `confirmed: true`, required reason and frozen request ID. Its logical result uses `recordId = requestId`, `revision = 1`, and complete per-row saved/rejected outcomes. Saved rows retain their original IDs and advance their source revisions once. They remain unpublished; no employee draft notices are queued.
- An active nonschedule-only, noncheckout actor needs explicit `schedule.manage`, using the same actor and department authority helpers as copy/individual scheduling. `location.manage` widens department scope but does not substitute for scheduling permission. Commands and receipt replay recheck current authority.
- Only future, unpublished, noncancelled, unreleased command-created drafts starting in the selected local week can save. A replacement also starts in that week; an overnight end may extend beyond it. Imported references, started/ended sources and drafts with any task, close or standard link require individual review. Authorized linked rows disclose link kinds, never task/close contents or answers.
- New employees/jobs require current same-store/department eligibility. Retained stations are revalidated against the new employee/job using the canonical helper; invalid stations reject the row rather than being cleared or remapped. Current station title/revision metadata is refreshed when the retained assignment saves.

## Deterministic valid subset

The backend implements the owner-selected [P05 policy](SCHEDULE_COPY_BATCH_DESIGN.md), including PR47's ready-only seed refinement:

1. Reject individually invalid rows, including fixed external-booking, person-wide approved-leave and store-specific approved-availability conflicts. Selected **local** old slots are excluded from fixed external booking checks and preserved in the private dependency projection. A foreign selected ID cannot remove an other-store booking from fixed checks.
2. Simultaneously reject both sides of every overlap between preflight-ready proposed new slots. Individually rejected proposals do not enter this seed set. No evaluation-order winner is chosen.
3. In simultaneous rounds, reject ready rows whose new slots depend on old slots retained by rejected rows. Repeat until no change. No rejected row is reinstated. An A→B→C chain propagates from C to B to A; a legal exchange saves together, while a failed exchange participant restores the old slot that rejects its partner.
4. Freeze the valid subset before writing. Each outcome includes its safe cause and rejection round; dependency source IDs appear only for sources the actor may read. An inaccessible dependency produces a generic overlap issue. Private person IDs, foreign bookings/leave and dependency graph context remain server-side.

The greatest-fixed-point claim is under this permanent two-sided-seed policy, not an optimization that selects winners among mutually conflicting proposals. Canonical ordering, simultaneous rounds and sorted causes make input permutations equivalent. Bounded 100-row cyclic exchange and worst-case rejection-chain checks use the normal runtime statement budget; no silent truncation or smaller undocumented cap is added.

## Atomic booking replacement and coordination

The command takes its store scope lock, then sorted NOWAIT scope locks for existing memberships of both old and proposed people, and selected source row locks after coordination. A held peer scope returns PostgreSQL `40001` / HTTP 503 `coordination_retry`; all rows, counters, audits and receipts remain untouched. Retry retains the exact original submission.

To permit a valid exchange with the existing immediate exclusion constraint, the transaction removes only **accepted** old rows from the private `person_shift_bookings` projection before updating shifts. Rejected sources and their old bookings remain. Normal per-row triggers insert every final accepted booking; the friendly checks and `person_shift_no_overlap` constraint remain enabled. The command checks final projection integrity before committing. No trigger, constraint, session replication setting or row-policy gate is disabled, and original shift rows are never temporarily cancelled or published.

Readers observe committed old or new schedules, not the transaction's temporary projection gap. A later audit/receipt/system failure rolls back the entire attempted subset, including deleted old projections and earlier accepted updates. Raw runtime access to the graph helpers/bookings remains denied. Shared adoption must keep this replacement inside the private coordinated write function and ensure every other person-booking/identity writer honors the same coordination contract; the candidate is not permission for uncoordinated privileged writes.

## Review freshness, time and retries

One read-only snapshot produces the plan. The digest binds canonical selected inputs, fixed source keys, selected old bookings, exact linked revisions, relevant employee/jobs/station/bookings/leave/availability/configuration, actor grants and source-review completeness. It does not bind global workspace or store-wide schedule counters. Unrelated task, checkout, goal, attendance or correction activity therefore does not stale an otherwise unchanged proposal. A changed relevant context refuses the **whole** old review with HTTP 409 `batch_review_changed`, before writes or receipt creation. There is no signing secret, stored review state or expiry.

Local time resolution rejects spring gaps and requires separate occurrence choices for newly ambiguous starts/ends. An unchanged ambiguous original with no choice retains its exact instant, including subsecond precision. Positive duration is bounded to 24 elapsed hours. Source/destination future checks sample one server instant per plan; passing a relevant start threshold changes the plan digest and requires refresh. Original source comparisons use explicit keys, not whole-row JSON equality.

One receipt contains the complete committed saved/rejected outcome. Same-ID replay precedes fresh eligibility, graph and completeness review, rechecks current authority and returns the original outcomes without attempting rejected rows again. Changed payloads conflict. After a known partial result, revise/review only rejected rows with current revisions under a new request; uncertain delivery first replays the frozen original. The existing coordination message applies, while actual outages/unrelated serialization failures stay `service_unavailable`.

Successful accepted updates advance the existing global workspace revision once and scheduling revisions through normal triggers. Older weekly publication reviews in the store remain invalidated even for unrelated weeks. Rollback, all-rejected results and receipt replay advance no such revisions. Source certification retains its separate input-revision contract.
