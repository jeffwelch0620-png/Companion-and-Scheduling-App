## Authentication outcomes

Missing, malformed, expired or invalid signed credentials return 401 `authentication_required`. Local key-set misses also require renewed credentials. The hosted remote resolver gives a newly encountered unknown signing-key ID a 30-second retryable 503 grace window, allowing jose's normal cooldown/refetch to recover a rotation. It never forces refetches from untrusted key IDs. A key still unknown after the window returns 401. Tracking is bounded to 100 key IDs; excess fresh misses are rejected rather than consuming unlimited memory. Transport/key-service failures stay 503 regardless of the grace timer. Actual hosted key propagation and rotation remain rollout checks.

A database session that is absent, expired, revoked or bound to another subject returns 401 at the identity resolver. Valid sessions with denied membership, location or action permissions still return 403. Signing-key transport, timeout, malformed key-service data and unexpected verification/configuration failures return a sanitized retryable 503; database failures continue to return 503. Unknown internal error types are deliberately not converted to forced sign-in. No failed verification grants access or enters a database transaction.

The change uses the existing private SQL session resolver error contract. Published migrations 001–036 remain byte-identical; no new migration is required. Read snapshots and write coordination from PR 26 are preserved. A 401 only means fresh credentials are required; it does not restore revoked membership or capabilities. Automatic Supabase refresh, sign-in/out, onboarding and session synchronization are still production integration work.

## Retained work and recovery

The durable IndexedDB queue still supports only employee task/closing readiness, including Dishwasher readiness represented as task transitions. Tokens are supplied at delivery time and never stored with commands. Expired/revoked sessions retain the exact command as `needs_auth`; permission denial blocks automatic resubmission. Temporary service failures and uncertain delivery remain pending. Login-provider errors raised before an HTTP command response receive the same classification.

The task and closing previews expose saved notes, creation time, delivery attempts and plain-language outcomes. An explicit retry keeps request ID, command, expected revision and original creation time. Reviewing old work permits another age-limited attempt without editing the original intent. HTTP 409 outcomes retain their status and offer Discard and redo instead of retrying unchanged work. Legacy non-age needs_review entries receive the same conflict treatment. The queue itself refuses conflict retries, so another caller cannot bypass the UI rule. Reload current work and check uncertain server delivery before creating a new intent. Retry remains available for queue_age_exceeded, blocked and needs_auth outcomes. Rejected/applied commands cannot be retried through this control. An expired crash lease can be recovered; an active delivery lease prevents retry, discard and clear.

Duplicate checking and entry insertion run inside the same IndexedDB read/write transaction across all entries for the employee/location/record, including different request IDs from separate tabs. Both previews use the shared retention helper; direct queue callers receive the same protection. Retrying the identical request remains idempotent. Pending/review/blocked/rejected copies block another intent until explicitly discarded; confirmed applied entries permit later work. Discard/clear remove the entries without a separate stale reservation. Assignment cache creation and employee cleanup share one escaped key builder, preserving the existing ordinary-key format and selected-record suffix.

Confirming conflict discard removes stale forms; checkout also removes its affected assignment cache. Connected recovery reloads current work; delayed recovery requires reconnecting before the form is available again. Reloading the delayed checkout page cannot restore the discarded stale assignment.

Discard and employee device-data cleanup require separate on-screen confirmation. They remove local copies, not server work; uncertain delivery must be checked with the manager before creating another submission. Clearing a selected subject atomically removes that subject's queue entries across locations, preserving other subjects and refusing active delivery. Checkout assignment caches for the selected preview actor are also removed, including prior fixture runs. The fixture directory/shared shell remain because they contain only fictional preview data. Clearing preview data is not hosted sign-out or remote-session revocation.

Subject partitions prevent accidental cross-employee delivery/display in these candidate screens; they are not an encryption or security boundary against another user of the same browser profile. Production shared-tablet authentication, logout cache retention, storage eviction/quota behavior, durable scheduling retries and phone/tablet checks remain open. Food prep queues require the Inventory data contract and are not implemented here.
