## Operator use and privacy

Run the wholly fictional example from the repository root:

```sh
node development/postgres-candidate/toast-roster-cli.mjs development/postgres-candidate/toast-roster.example.csv development/postgres-candidate/toast-roster-context.example.json
```

Exit 3 means preparation needs review; exit 1 means input was refused. Successful output contains source names, employee GUIDs and reported jobs: it is a sensitive operator artifact. For authorized real inputs, retain it only in owner-controlled private storage; never commit, paste into public logs or attach it to a PR. Errors use a fixed code without paths, source fragments or exception text. Input files are read-only; the command writes only its output stream, opens no database and makes no network requests. The example and tests are authored wholly fictional data, independent of employee exports.

The context file explicitly supplies source/store/tenant/timezone bindings, captured time, active-only scope/effective-date review and paired-job review status. A reviewed expected Location label guards against the wrong store's file; the display label does not establish authority. Neither a caller-supplied reviewer nor a matching label proves authorization, population coverage, completeness or current access. The real source's job/scope semantics still require review; use `unverified` pairing until reviewed. No real workbook, source file or detailed operator report is included in this PR.

## Implemented contract

- Exact ordered ten-column Toast roster header. UTF-8 with optional BOM, LF or CRLF, comma quoting/escaped quotes and positional semicolon job pairs are supported. Unknown/reordered/missing headers, malformed CSV, invalid names/GUIDs, duplicate employee GUIDs, duplicate job pairs, mixed/mismatched locations and mismatched job lists refuse the whole preparation without partial output. Empty exports require separate scope review.
- Limits are 2 MiB source bytes, 2,000 employees, 100 jobs per employee, 2,000 characters per CSV field and 16 KiB CLI context. Bounds refuse rather than truncate. These are preparation safeguards; S05 production-volume/retention selection remains pending.
- Provider-only `source-content-v2` fingerprints cover scope/profile/transform, employee GUID, trimmed name and job-token/description pairs. Tokens retain exact text, descriptions are trimmed, pairs sort ordinally by token then description, and duplicate pairs are refused. Unknown/non-UUID tokens hash deterministically and remain unresolved. Conflicting descriptions for the same token flag every affected member. Excluded contacts, phone, wages, legacy display ID and Location label do not enter member fingerprints or prepared records.
- Department, primary job, scheduling-job selection and schedule-only participation remain in a separately revisioned/reviewed manager supplement. `sourceReviewContextDigest` binds the supplied supplement choices/reviewer/revision, target input revision, access fence and freshly recomputed provenance digest. It validates the digest envelope, not the supplement's business rules or authority. Callers must normalize current bytes/context again; never trust a stored digest as a signed review token. No supplement editor or application path is implemented.
- Raw-file SHA-256, normalized-source digest and provenance digest are separate. Canonical JSON sorts object keys and retains positional array order; only the documented job set is sorted. Exact explicit timestamps become signed UTC microsecond strings with strict calendar validation. Capture/population/pairing/location evidence is provenance, not provider content. Name/job changes stale source mappings; supplement changes stale review context without changing sourceVersion.
- The output is `toast-roster-preparation-v1`, a separate intermediate artifact, **not a supported V3 preview envelope**. It invents no provider `active` field, integer revision, department, primary job or access grant. Leave is unavailable. Roster coverage remains unverified and every record requires manager supplement and identity review. All output keeps `canApply`, `completenessCertified` and `accessProvisioned` false. Existing V1/V2 preview contracts remain unchanged and refuse this artifact.
