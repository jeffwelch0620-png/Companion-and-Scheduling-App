## Authority and application

Corrective 055 adds explicit `schedule.correct` to the candidate capability contract without granting it to any existing membership. Active, nonschedule-only actors outside the configured checkout position may correct their own department; adding `location.manage` expands that explicit correction permission to the store's operating departments. A title, ownership notice target, ordinary schedule permission or location-management grant alone does not grant correction access. During shared adoption map this permission to the owner-selected GM/ownership and explicitly designated department managers; provisioning remains separate.

`correction.propose` binds a published, noncancelled, ended source revision and the current ledger revision (zero before the first proposal). Corrections to another employee apply with a required reason. A proposal for the author's own person remains pending, preserving the original/last applied summary until approval. Independent approval is still required for completed-shift corrections; the separately retained attendance self-review policy does not remove it.

`correction.approve` and `correction.reject` require a person distinct from both author and subject, including across memberships. Approval rechecks the current author's correction permission, the approver's permission, exact source snapshot and proposal's applied-version baseline. Rejection may close a stale/revoked-author proposal without applying it. `correction.withdraw` is reserved to the currently authorized author. A pending proposal cannot be overwritten; reject/withdraw it before proposing again. All decisions require a note. Each ledger has the existing-style 1,000-event ceiling.

The command acquires `lock_scope` before policy or record locks and reads server time after coordination. It accepts only planned start/end/job and a reason, with explicit offset-based instants, valid calendar/clock values, a positive period of at most 24 hours and an end no later than the current server clock. The duration matches the existing scheduling bound. Future/active shifts use ordinary scheduling commands. Employee/store/department/station/state changes require separate reconciliation. Historical job corrections do not grant eligibility or reroute original work.

## Immutable source and separate effective summary

The correction row stores original member/person, department, source revision and full source snapshot, captured timezone/local date, historical employee name, last applied summary/version, last proposal, author and decision state. Its origin is guarded against updates. Correction functions serialize snapshots and events under UTC so changing a database session timezone cannot change source comparisons or audit chains; the captured store timezone still determines historical local dates/display. New proposals/decisions append before/after events, retaining rejected and withdrawn proposals. Current employee/author names resolve at read time, separately from labelled names at time of entry. Replay checks current correction access and the event's original actor person before returning the existing receipt; mutable source/status checks follow receipt lookup for new commands only.

Applying a correction never updates the original shift, bookings, staffing, attendance, completed tasks, closing answers/checks, guide snapshots, their audit or prior receipts. Retained task/closing links are surfaced as review warnings. Source drift blocks new application and is visible in correction detail. Existing applied summaries survive later pending/rejected/withdrawn proposals. Planned-hours/labor consumers must eventually use the effective applied summary (or original if none); these values remain planned details and do not establish actual worked hours/pay. No consumer is connected here.

## Ownership notice bridge and atomicity

The current shared owner configuration is not available to this isolated package. `completed_shift_notice_policy` is a **private fictional provisioning bridge**, never production ownership authority. It represents owners plus admins explicitly enabled by a current owner. An active owner and resolvable auth-linked recipients are required. Invalid enabling-owner relationships or unresolved accounts hold application with `ownership_notice_unresolved`. An own-shift pending proposal may await configuration, but approval cannot apply until resolution succeeds.

Replace `correction_notice_recipients` with a read of the current shared owner model during the shared-authz port, then remove the bridge/provisioning fixtures. Do not deploy or freeze this table as a parallel production recipient list. Runtime credentials cannot read or change it. Privileged bridge writes use NOWAIT store coordination, so competing writers receive `40001` and must retry the whole transaction. Bridge edits advance correction/global freshness, since they change possible application/actions.

Ledger, event, correction/global increments, receipt and one minimal outbox intent per resolved recipient commit together. Intents contain correction/shift/revision identifiers only, with no correction reason or attendance narrative. Replays do not add intents; late notice/receipt failure rolls back every effect. Actual notification delivery remains a separate workflow.

## Private reads

- `GET /completed-shifts`: paged eligible ended sources, original/effective summaries and server proposal flags. The first page returns `asOf`; subsequent pages must reuse it, so shifts ending during the drain do not enter its selection. Compare `scheduleRevision` too when draining sources, since source writes can change eligibility without touching the correction ledger. Future/nonfinite cutoffs are refused.
- `GET /completed-shifts/:shift`: current source version plus captured original identity/summary if a ledger exists; exact ledger revision and proposal flag.
- `GET /shift-corrections` and `/:id`: scoped ledgers, latest proposal/effective summary, warnings and server-computed decision flags, including stale sources for rejection/history.
- `GET /shift-correction-history/:id`: complete ascending event cursor (`after` 0–1000), pages of 1–100, current/historical names, before/after snapshots and `recordRevision` distinct from store-wide `correctionRevision`.

Every HTTP read uses the existing trusted session resolver and read-only repeatable-read transaction. Read entry points acquire no coordination lock; employee and foreign-department reads fail closed. Correction data never joins general employee schedule reads. Lists use UUID pagination, explicit completeness and store/department filtering. The later UI must recheck relevant current authority before/after a drain and bind the correction/entry versions; source-picker drains additionally bind the frozen cutoff and schedule version. Detail includes current source revision so exact source drift can be checked without treating unrelated scheduling writes as ledger changes. The new correction counter advances for correction commands and notice-policy edits, while unrelated task, attendance and scheduling commands do not advance it. Correction writes do not advance schedule, source-input or attendance counters or stale reviewed weekly planning.
