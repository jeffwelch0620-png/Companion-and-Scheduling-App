## Purpose and limits

Exercise selected proof-binding, independent link-evidence and uncertain-provider-state rules from the accepted [onboarding design](PERSONAL_ONBOARDING_INTENT_DESIGN.md) while Inventory's tested baseline/catalog remains pending. The [pure oracle](onboarding-intent-rehearsal.mjs) is imported only by its [fictional tests](onboarding-intent-rehearsal.test.mjs). No active application, adapter, UI or CLI calls it. It performs no networking, database/provider reads, writes, account setup, audit/receipt/outbox creation, permission grants or reconciliation resolution.

All verified/current/eligible/owner/admin/contact-confirmation/attestation/operation flags, canonical contact strings, revisions and clocks are supplied fictional fixtures. They prove no actual authentication, authorization, ownership, account control, provider operation or elapsed-time security property. The module is deliberately not a full link-approval or setup-issuance predicate. Its issuerEligible flag stands for a supplied current aggregate eligibility judgment, not an implementation of scoped issuer grants or membership epochs. Organization/person/session/link/store lifecycle fences and uniqueness need the future shared implementation.

Every result is labelled fictional and non-authoritative, with canApply, accessProvisioned and completenessCertified false. eligible means only that this narrow supplied-fixture predicate passed. Results contain fixed codes, flags and optionally three proposed state axes; no person IDs, subjects, contacts, evidence records or operation references. Malformed/unsupported fixtures throw only the fixed TypeError `invalid_onboarding_intent_rehearsal`. Plain-object exact shapes, bounded strings and safe counters are rehearsal input safeguards, not owner-selected product limits.

## Rehearsed contracts

| Function | What the fictional examples check | What remains outside the oracle |
| --- | --- | --- |
| rehearseOnboardingProofBinding | Current verified proof binds exact organization/person/intent/revision/audience/challenge; configured provider/issuer/tenant and subject compare exactly. First valid proof reports binding required; later proof cannot replace that identity. | No binding write, uniqueness/locking, cryptographic validation or concurrent first-proof race test. A sequential later-lock fixture is not concurrency proof. |
| rehearseOnboardingLinkEvidence | Recorded binding and expected intent/binding revisions; current verified owner/admin reviewer from another canonical person; A03 usable-contact prerequisite; exact pre-issuance authorized contact reference/revision/author/time; issuer-created contact needs the independent reviewer's confirmation or own account-control attestation. Attestation binds exact person/intent/revisions/account and reviewer. | No complete authorization, contact repository, provider transport, legal-identity proof or actual link commit. Comparing already canonical contact strings chooses no email/phone normalization policy. No fuzzy/name/source matching. |
| rehearseOnboardingTransition | A recorded original-operation fixture precedes pending state; timeout means unknown plus reconciliation required. Expiry/revocation preserves pending/unknown operation state; verified confirmation of that exact original operation never implicitly clears required reconciliation or grants access. | No calls, operation persistence, idempotency guarantee, actual state mutation, link event, provider refusal/reissue workflow or reconciliation resolution. |

Setup states are supplied as approved/expired/revoked/consumed; provider axes are supplied separately. provider_started requires a fixture stating that the original operation has already been recorded; the model's proposed pending result is not permission to contact a provider. approval_expired is a supplied event, not an implemented product TTL. No rates, durations, attempt caps, leases, delivery channel or provider API are selected. The future transaction must store operation correlation before a supported external call, commit proof locks under coordination, recheck current eligibility, preserve unknown outcomes and reconcile using supported provider evidence.

A changed captured contact is refused even when optional attestation is also supplied; the manager must refresh/reissue the stale review context rather than silently drop stale evidence. Issuer-created contact ownership confirmation is represented by the independent current owner/admin reviewer and bound contact revision; actual collection/verification and evidence custody remain to implement. In-person evidence requires that reviewer's own attestation of the intended person's control of the locked account, not an issuer claim. It bypasses neither current provider authentication nor A03.
