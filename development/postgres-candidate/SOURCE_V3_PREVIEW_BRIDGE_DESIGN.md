Keep `firstName` and `lastName` separate in provider fingerprints; `displayName` is presentation only. Keep exact source job tokens paired with descriptions, including unresolved non-UUID tokens. ## Supplement identity and choice schema

Use one supplement document per explicit reviewed source/store scope. Its envelope contains its own positive integer revision, reviewer, reviewedAt instant, choices, and a population binding with positive integer revision and effectiveDate. That population revision/effectiveDate must exactly match the artifact provenance; refuse the whole supplement with `supplement_population_mismatch` when either differs, rather than attaching its choices to a different population. Each choice retains its reviewer, positive revision and reviewedAt from the manager review. These are supplied review facts, not proof of reviewer authority; later shared review must resolve the current session and designation independently.

The explicit namespace is the tuple `(organizationId, system, tenant, storeId, externalStoreId)`. A workbook J-key is resolved back to the exact provider token before constructing a choice; it never becomes a source or canonical identity. Names cannot supply the key.

| Choice kind | Identity within the namespace | Required decisions |
| --- | --- | --- |
| job | exact job token | Explicit configured department and position/job key, and allowScheduling boolean. No title-derived capability or default department. Preserve the provider description separately. |
| tokenReview | exact job token | Explicit provider_job_key, retired_job or not_a_job semantics; exact observedDescriptions set, canonicalDescription text/null and reviewer/revision/reviewedAt. A conflicting description set requires a canonical display acknowledgement. |
| member | exact employee sourceId | Explicit primaryJobToken, schedulingJobTokens set and scheduleOnly boolean. Empty schedulingJobTokens means reviewed no scheduling jobs; a missing selection remains missing. |

Primary and selected scheduling tokens must occur in that employee's provider job set. The proposed membership department is the department mapped for the member's PRIMARY job token. That primary token requires a reviewed job mapping even when allowScheduling is false or schedulingJobTokens is empty; without it, emit row-level blocking `primary_job_mapping_required`. Each selected scheduling token requires a reviewed job mapping; a missing selected-job mapping produces `job_mapping_required`. If any reviewed mapping names a department or position/job key absent from the target store configuration, emit distinct row-level blocking `target_job_configuration_required` rather than treating it as an absent mapping. A selected scheduling job whose mapped department differs from the primary department produces row-level blocking `cross_department_scheduling_review`: existing authority and eligibility retain the single-primary-department behavior recorded in PR51. A scheduling token with allowScheduling false is refused. A nonschedulable primary job may still define membership department and position while schedulingJobTokens is explicitly empty. Both regular and schedule-only participation require separate identity/access review; neither creates a login or membership approval. A no-job employee remains unresolved even if someone supplies a guessed primary job. Unknown token semantics, conflicting token descriptions, unverified pair associations and source exceptions must be resolved explicitly, never cleared by merely supplying a canonical label.

The implemented [supplement checkpoint](MANAGER_SUPPLEMENT_CHECKPOINT.md) specifies tokenReview freshness and exclusion findings. Only a fresh provider_job_key resolution permits an unresolved token to become a mapped/selected job. Retired/non-job decisions override UUID shape, exclude mapping and selection, and preserve original provider pairs/fingerprints. New observed descriptions stale the prior review; a canonical display label changes only supplement context. No-job member choices use member_choice_for_no_job_employee.

V3 MUST construct selection review's providerMembers from the FULL validated store roster after preparation/provenance/count recomputation, including unselected employees and members without choices. Build cross-roster token/description conflict checks before filtering any selection or displayed report. A partial-selection caller must not hide another employee's conflicting description. The current pure supplied-projection function cannot establish completeness itself; enforce this when implementing the bridge, with a partial-selection conflict acceptance case.

Before connecting the current sourceReviewContextDigest helper, canonicalize the documented choice set by `(namespace, kind, sourceId-or-token)`, using fixed ordinal tuple comparison, and reject duplicate identity keys even if their decisions are identical. Canonicalize schedulingJobTokens as a documented set with duplicate refusal. Preserve exact token spelling; do not case-fold or trim keys. Preserve positional arrays elsewhere. Reordering identical choices or selected-job sets must retain the supplement digest; changing choices, revision or review metadata must change it. Scope distinctions prevent one store's job/member choice from satisfying another store's requirement.

This supplies the schema prerequisite for the ordering item tracked in PR57. The existing helper still retains supplied choice order until this implementation is reviewed; this document does not claim the behavior is implemented.

## Reports and completeness

Malformed envelope/version/digest/duplicate-key input refuses the input with fixed minimized errors. Record-level missing jobs, unresolved job mappings, absent supplements and stale aliases produce per-row findings while retaining other rows in the report. Distinguish blocking findings from reconciliation-required findings; preserve an omitted target record as an explicit review obligation. Detailed reports and normalized names/GUIDs/jobs are private operator artifacts, never public PR attachments, fixtures or logs.

An inspectable row or reviewable active population is not certified complete. All results retain `canApply:false`, `completenessCertified:false` and `accessProvisioned:false`. Unsupported jobs, missing decisions, source/target drift or incomplete evidence cannot be bypassed by a successful parse, supplied reviewer name or manufactured coverage flag. Future application remains atomic per declared completeness scope under S03; schedule copy/batch partial saves are unrelated. Preserve current leave/availability, shared identity and separate capability gates before scheduling adoption.

## Required membership and population acceptance cases

- A member with a reviewed nonschedulable Kitchen primary and no selected scheduling jobs proposes Kitchen membership department and the mapped primary position, without creating scheduling eligibility. A same-department schedulable additional job may be selected when its mapping permits it.
- A Kitchen primary plus a selected Service scheduling job retains the report row and emits blocking `cross_department_scheduling_review`; do not switch department, create a second membership or discard the selected job.
- A primary token present in the provider job set but without a reviewed job mapping emits blocking `primary_job_mapping_required`, even when no scheduling jobs are selected.
- A reviewed mapping referring to an unconfigured department/job produces `target_job_configuration_required`; an absent selected-job mapping instead produces `job_mapping_required`. Never create target configuration as a side effect.
- A supplement with matching population revision/effectiveDate can be validated; a differing revision or effectiveDate refuses the whole supplement before row evaluation. Both binding values participate in its canonical digest and the complete review context.
