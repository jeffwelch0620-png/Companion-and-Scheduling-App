## Component and scope model

An immutable component records original actor and target canonical people, organization, exact ordinary capability/store/department, owner or enabled-admin basis, verified-at-approval fixture, captured admin epoch for admin basis, membership identity/epoch and component identity. Scope increments are separate components: an owner-approved baseline is not relabelled when an admin adds another department. Owner-basis components use no admin epoch. Grants to other canonical people do not become self-grants because the granting admin is disabled.

This rehearsal covers **store employment-dependent ordinary grants only**. Protected organization owner/admin authority, source-review designations, account links and unrelated permission families are outside its ordinary registry. A registered ordinary key is supplied as reviewed metadata, not inferred from titles or browser input. Employment must remain approved and non-schedule-only with its captured membership epoch; rehire cannot revive an old component.

Each pending obligation is keyed by canonical person plus one exact capability/store/department atom; the organization is bound by the containing policy. The key never means “current admin.” Identical permission scopes for A and B remain separate, while UUID case variants for the same person/scope are duplicates. Each scope is one exact capability/store/department atom. Before this model can be used, a trusted fictional normalizer must already have expanded any broad/template permission extent to a complete set of canonical atoms. The scopeExpansionVerified flag is not an implementation or proof of that expansion. Wildcards are refused; hierarchy, organization/store-wide inheritance, dynamic catalogs and production overlap normalization are not implemented. The shared port must implement and test trusted expansion/overlap against its actual catalog before using set equality. Never feed unexpanded broad grants or accept these fixture flags from a client.

UUID case variants compare as the same identity. Capability and department keys compare exactly under the supplied canonical registry; no title or case guessing. Changing component/receipt/template IDs does not change a suspended exact permission extent. List bounds of 200 and bounded strings are input safeguards for this oracle, not selected organization/grant-size limits.

## Rehearsed predicates

| Function | Fictional check | Exclusions |
| --- | --- | --- |
| rehearseAdminSuspensionTransition | One declared consecutive admin-switch event, current owner fixture, expected policy revision, verified complete component history and scope expansion; disable or seat reassignment advances the epoch once and retains all earlier unresolved person-scoped extents plus the outgoing enabled admin’s active self-grants. Re-enable/no-op cannot clear them. Audited real changes advance the policy revision. | No actual mutation, complete-history query, persisted audit, lock or proof that every concurrent writer used this policy. Supplied completeness is not certified completeness. |
| rehearseOperationalGrantUse | Current membership lifetime plus ordinary verified provenance; disabled self-admin components fail, outstanding exact extents survive new IDs/epochs, stale/future self-admin epochs fail. Owner-approved components and grants to others are checked under their own lifetime. | This is not full authorization, department/training clearance, current session proof, grant creation or permission administration. It does not collect reasons/audit for a new self-increase or implement A01. |
| rehearseOwnerSelfGrantReconfirmation | Current verified eligible owner fixture, exact organization/person/pending extent, expected policy revision, current employment/membership epoch, registered ordinary scope, required reason and audit. | Success clears nothing and grants nothing. The shared writer must atomically create a new owner-based component, reconcile only the reviewed obligation, and record audit/receipt after coordinated rechecks. |
| rehearseGrantProvenanceStability | Same-record immutable original actor/target/basis/epoch/scope/membership provenance; old admin components cannot be relabelled owner-based or refreshed after rehire. | Stability alone authorizes no active/revision change. It verifies no historical owner authority, audit or write. |

The owner selected direct atomic A → B reassignment. It means disable-for-A plus enable-for-B, requires current-owner authority, complete history, audit and the expected policy revision, advances the epoch once and suspends A’s active self-granted extents. A reassignment, even from an already disabled seat, advances epoch and policy revision; a true → false switch also advances epoch once; enabling the same seat preserves epoch; a no-op advances neither. The future coordinated writer must commit the seat, counters, A’s obligations and audit/receipt together or none. These are snapshot examples, not proof that real provider/organization lifecycle lapses were captured. Current owner authority, original verified basis and complete scope/history must come from future trusted server-side services.

Only historical self-grants (actor person equals target person) depend on the current admin seat, its enabled state and epoch. A verified enabled-admin-basis grant issued to another person does not consult current seat identity/state/epoch; it retains its own membership/epoch lifetime. Former-admin self-grants remain unusable after the seat moves. B’s fresh self-grant is unaffected by A’s pending scope; any B obligation still applies to B.

Owner reconfirmation can occur for the exact named person after that person loses the admin seat, or while the admin switch remains disabled. It uses current owner authority, rather than requiring admin re-enablement. A person independently holding current owner authority may act under that owner basis, consistent with A04.3; an admin without owner authority cannot reconfirm. This does not change different-person onboarding link review or own-shift correction approval. Old admin provenance remains unchanged after a new owner component is approved; enabling admin or clearing an obligation does not refresh an old captured epoch.

The source predicates contain no receipt/template field that can bypass semantic checks. Production must enforce immutable provenance, complete canonical scope overlap and the shared organization/person/store lock order across disablement, self-increase, reconfirmation and replays. These sequential fixtures do not prove atomicity, lock coverage, final access fences or receipt replay.
