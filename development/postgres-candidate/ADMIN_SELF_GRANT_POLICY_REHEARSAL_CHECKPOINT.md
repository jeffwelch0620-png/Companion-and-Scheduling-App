## Component and scope model

An immutable component records original actor and target canonical people, organization, exact ordinary capability/store/department, owner or enabled-admin basis, verified-at-approval fixture, captured admin epoch for admin basis, membership identity/epoch and component identity. Scope increments are separate components: an owner-approved baseline is not relabelled when an admin adds another department. Owner-basis components use no admin epoch. Grants to other canonical people do not become self-grants because the granting admin is disabled.

This rehearsal covers **store employment-dependent ordinary grants only**. Protected organization owner/admin authority, source-review designations, account links and unrelated permission families are outside its ordinary registry. A registered ordinary key is supplied as reviewed metadata, not inferred from titles or browser input. Employment must remain approved and non-schedule-only with its captured membership epoch; rehire cannot revive an old component.

Each scope is one exact capability/store/department atom. Before this model can be used, a trusted fictional normalizer must already have expanded any broad/template permission extent to a complete set of canonical atoms. The scopeExpansionVerified flag is not an implementation or proof of that expansion. Wildcards are refused; hierarchy, organization/store-wide inheritance, dynamic catalogs and production overlap normalization are not implemented. The shared port must implement and test trusted expansion/overlap against its actual catalog before using set equality. Never feed unexpanded broad grants or accept these fixture flags from a client.

UUID case variants compare as the same identity. Capability and department keys compare exactly under the supplied canonical registry; no title or case guessing. Changing component/receipt/template IDs does not change a suspended exact permission extent. List bounds of 200 and bounded strings are input safeguards for this oracle, not selected organization/grant-size limits.

## Rehearsed predicates

| Function | Fictional check | Exclusions |
| --- | --- | --- |
| rehearseAdminSuspensionTransition | One declared consecutive admin-switch event, current owner fixture, expected policy revision, verified complete component history and scope expansion; disable advances the epoch once and retains all earlier unresolved extents plus active admin-derived self-grants. Re-enable/no-op cannot clear them. | rehearseOperationalGrantUse | Current membership lifetime plus ordinary verified provenance; disabled self-admin components fail, outstanding exact extents survive new IDs/epochs, stale/future self-admin epochs fail. Owner-approved components and grants to others are checked under their own lifetime. | This is not full authorization, department/training clearance, current session proof, grant creation or permission administration. | rehearseOwnerSelfGrantReconfirmation | Current verified eligible owner fixture, exact organization/person/pending extent, expected policy revision, current employment/membership epoch, registered ordinary scope, required reason and audit. | Success clears nothing and grants nothing. The shared writer must atomically create a new owner-based component, reconcile only the reviewed obligation, and record audit/receipt after coordinated rechecks. |
| rehearseGrantProvenanceStability | Same-record immutable original actor/target/basis/epoch/scope/membership provenance; old admin components cannot be relabelled owner-based or refreshed after rehire. | Stability alone authorizes no active/revision change. It verifies no historical owner authority, audit or write. |

The fictional counter convention is explicit: a consecutive true → false switch increments the admin epoch; enabling preserves that advanced epoch; a changed switch advances its policy revision and a no-op advances neither. These are snapshot examples, not proof that real provider/organization lifecycle lapses were captured. Current owner authority, original verified basis and complete scope/history must come from future trusted server-side services.

Owner reconfirmation can occur while the admin switch remains disabled. It uses current owner authority, rather than requiring admin re-enablement. A person independently holding current owner authority may act under that owner basis, consistent with A04.3; an admin without owner authority cannot reconfirm. This does not change different-person onboarding link review or own-shift correction approval. Old admin provenance remains unchanged after a new owner component is approved; enabling admin or clearing an obligation does not refresh an old captured epoch.

The source predicates contain no receipt/template field that can bypass semantic checks. Production must enforce immutable provenance, complete canonical scope overlap and the shared organization/person/store lock order across disablement, self-increase, reconfirmation and replays. These sequential fixtures do not prove atomicity, lock coverage, final access fences or receipt replay.
